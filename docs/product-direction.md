# Ariadne 제품 방향

2026-11-03 사용자 방향 정정. 이 문서가 제품 목표·범위·우선순위의 정본이다.
현재 제공 기능은 [README](../README.md), 실행 조건은 [실행 정책](execution-policy.md), 기술 계약은 [통합 실행 설계](unified-execution-design.md)가 소유한다.

## 사용자가 원하는 결과를 끝내는 통합 에이전트 하네스

사용자는 원하는 일을 설명한다. Ariadne는 목표와 완료 조건을 유지하고, 필요한 문맥·도구·실행기를 연결해 결과를 확인하는 역할을 맡는다. 같은 요청을 다시 설명하거나 도구 사이에 자료를 옮기는 수고와 불필요한 모델 사용을 줄이는 것이 제품 목표다.

코딩·조사·문서 작성·분석·반복 업무를 작업 유형으로 다룬다. 특정 사용자 집단이나 저장소 종류가 제품 범위를 정하지 않는다. 실행 가능한 범위는 연결한 도구의 기능과 사용자가 허용한 권한·데이터·예산으로 정한다. 로그인이나 도구 등록만으로 새로운 실행·과금·외부 발송이 승인되지는 않는다.

이 정의는 목표다. 현재 코어·기억·코드 분석·도구 연결 기반이 모든 유형의 작업을 자동 완주하는 제품으로 완성됐다는 뜻은 아니다.

## 기능 묶음보다 작업을 중심에 둔다

검토한 방향은 다음과 같다.

| 방향 | 구조와 결과 |
| --- | --- |
| 코딩 도구에 다른 기능을 계속 추가 | Git·코드 변경을 공통 입력으로 삼아 비코딩 작업도 같은 틀에 맞춰야 한다. |
| **공통 작업 흐름에 분야별 도구를 연결** | 목표·문맥·권한·예산·검증은 공유하고, 자료 수집·문서 편집·코드 분석은 필요한 작업에서 선택한다. |

두 번째 방향을 따른다. 저장소·Git·worktree는 코딩 작업의 자원이며, 일반 작업의 필수 조건으로 만들지 않는다. 기존 데이터·도구 계약은 유지하고 이를 포괄하는 작업 계약부터 구체화한다. 분야별 새 추상화나 실행기를 한꺼번에 만들지는 않는다.

## 하네스가 맡을 책임

1. **목표와 완료 조건:** 원하는 결과·제약·현재 결정을 하나의 작업 기록으로 유지한다. 확인된 내용을 다시 묻지 않고, 실행에 필요한 정보가 빠졌을 때 확인한다.
2. **필요한 문맥:** 자료의 출처·관련성·최신성을 확인하고 필요한 부분을 전달한다. 목표·권한·완료 조건을 잘라서 예산만 맞추지 않는다.
3. **도구와 실행기 연결:** 승인·필수 기능·품질을 충족하는 후보를 고른다. 사용자의 명시 지정을 우선하고, 한 실행기로 충분하면 역할이나 공급자를 늘리지 않는다.
4. **진행과 결과 확인:** 접수·실행·종료·성공을 구분한다. 실패 원인과 외부 효과를 확인한 뒤 재시도하고, 작업이 끊겨도 결정과 근거를 이어 간다.
5. **사용량 관리:** 탐색·라우팅·실행·검토·실패·재시도의 관측 가능한 모델 사용량을 같은 작업에 귀속한다. 하네스가 절약하려고 추가한 호출도 비용에 포함한다.

모델은 판단과 생성, 도구는 검색·조회·변경·검증을 수행한다. Ariadne가 모든 도구를 재구현하거나 공급자의 인증·세션·실행 루프를 임의로 대체하지 않는다. 도구 결과와 외부 문서는 근거이며 실행 권한의 원본이 아니다.

## 토큰 낭비를 줄이는 기준

작은 모델이나 짧은 프롬프트 자체를 목표로 삼지 않는다. 필요한 문맥과 검증을 지키면서, **합의한 완료 조건을 만족한 결과를 얻는 데 든 전체 사용량**을 비교한다. 실패로 버린 사용량도 빠뜨리지 않는다.

우선 줄일 것은 반복 설명, 같은 입력의 중복 탐색, 변경 없는 전체 문맥 재전달, 근거 없는 재시도, 목적 없는 다중 실행이다. 같은 입력·범위·환경에서 확인한 결과는 재사용한다. 날짜나 원본이 바뀌면 영향을 받는 근거부터 갱신한다. 정확히 계산하거나 조회할 수 있는 일은 모델을 호출하지 않는다.

| 확인할 것 | 판정 방법 |
| --- | --- |
| 완료 품질 | 작업 전에 고정한 완료 조건·사실 정확성·권한·데이터 보존 조건을 충족했는지 확인한다. |
| 모델 사용량 | 입력·출력·캐시·추론의 공급자별 계측 정의를 고정하고 중복 합산하지 않는다. 관측할 수 없으면 `unknown`으로 남긴다. |
| 재작업과 시간 | 실패·재시도·사용자 재설명·완료까지 걸린 시간을 함께 기록한다. |
| 비교 조건 | 같은 작업·입력·품질 기준에서 하네스 사용 전후를 비교하고 모델·도구·설정 차이를 기록한다. |

토큰을 덜 쓰고 품질 기준을 놓쳤다면 성공한 절감으로 보지 않는다. 토큰 수를 구독 잔여량이나 금액으로 임의 환산하지 않는다. 현재의 로컬·CI 통과는 구현 검증이며, 실제 작업의 토큰 절감 효과는 아직 측정하지 않았다.

## 다음 구현의 우선순위

| 순서 | 만들 것 | 완료를 확인할 방법 |
| --- | --- | --- |
| 1 | 비코딩 작업도 표현하는 공통 목표·완료 조건·근거·권한·예산 계약 | 조사·문서 작업을 코드 저장소 없이 표현하고 기존 코딩 계약도 보존한다. |
| 2 | 실행기 하나와 필요한 도구만 사용하는 작업 한 종류의 처음부터 끝까지 흐름 | 실제 도구로 시작·진행·결과 확인·중단·재개를 검증한다. 수동 연결과 자동 실행을 구분한다. |
| 3 | 필요한 근거의 선택·최신성 확인·재사용과 작업별 사용량 관측 | 자료 하나를 바꿨을 때 영향 있는 근거만 갱신하고 전체 호출·실패 사용량을 설명한다. |
| 4 | 같은 품질 기준의 비교 평가 후 필요한 분야·실행기로 확장 | 하네스 자체 비용을 포함한 결과를 보고 유지·축소·개선 여부를 결정한다. |

기존 코딩 분야의 안전·복구·완료 판정 설계와 인수 기준은 재사용한다. 선택한 실행 경로의 필수 검사를 생략하거나 미완료 dispatcher를 활성화하지 않는다. 각 단계의 실제 도구·권한·계측 지원을 확인한 뒤 구현 REQ로 범위를 고정한다.

예를 들어 “이 자료를 조사해 근거가 있는 보고서를 만들어 줘”라는 요청에서는 조사 범위·최종 산출물·출처 기준을 작업으로 유지한다. 검색·요약·작성·검토가 같은 근거를 공유하고, 새 세션에서도 처음부터 다시 수집하지 않는 것이 목표다. 자료 하나의 결론이 바뀌었을 때 관련 주장과 검증만 갱신할 수 있는지가 전이 점검이다. 이 사례의 자동 실행은 아직 제공하지 않는다.

이전 프로젝트의 출처·설치 통합·보존 이력은 [운영·이관 문서](consolidation.md)에 둔다. 사용자에게는 무엇을 맡길 수 있고, 어디까지 확인했으며, 무엇이 남았는지를 먼저 설명한다.
